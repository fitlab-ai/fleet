# 跨平台测试范围

## 平台范围与守卫

- 每组平台相关测试都应说明实际宿主 OS、架构、权限和外部工具版本，并区分纯契约测试、
  真实系统集成测试与人工验证。模拟进程或 runner 的通过不能证明真实信号、sudo、TUN 或系统代理行为。
- 不依赖平台能力的纯 Go 契约测试应在当前平台正常运行，不能为方便而跳过。
- 平台专属测试使用 Go 原生文件后缀或 `//go:build` 限定编译范围；运行时前置条件
  （权限、外部二进制、网络或受控节点）不足时，使用带明确原因的 `t.Skip`，不能静默 return。
- 交叉编译只能证明目标平台可编译，不能替代在真实目标平台运行测试。

## 执行与证据

- 按 `testing-discipline.md` 执行构建、vet、全量单测和 race 检测；变更涉及生命周期、
  取消、超时或共享状态时，必须保留竞态检测的结果。
- 记录实际 pass、fail、skip 数和未执行范围。外部工具缺失导致的 skip 不得计为对应集成验证通过。
- 临时端口、目录、进程及全局状态必须隔离和清理；测试应验证必要的资源释放和所有权边界。
- 平台专属能力必须在相应真实平台验证。当前 CI 的 Ubuntu 测试不能证明 macOS 系统代理、
  TUN 权限或资源恢复正确，也不能用伪造 OS 标识、路径或返回值代替真实平台执行。
- 当前环境无法完成的真实平台验证，记录具体场景、前置条件、步骤、期望结果及未执行状态，
  作为 manual-validation 保留；不得将环境缺失误报为已复现的业务缺陷。

## 审查出口

审查报告记录本规则加载情况、受影响平台、守卫/跳过证据、实际运行范围和剩余人工验证。
可复现的平台缺陷进入 finding；未加载必读规则或未分类的实际平台风险仍是审查缺口，
不能以结构校验或其他平台的绿色测试替代。人工验证数量不改变 review-code 既有结论规则。
